# 莲心视觉实验室开发方案

## 1. 项目目标

建立一个独立于莲心主程序的本地视觉感知实验室，用于逐步验证并整合：

- 人脸识别
- 手势识别
- 陪伴与工位检测
- 本地视觉事件记录

第一阶段不接入 LLM、Qwen-VL、云端视觉服务、视频上传或后台监控。所有摄像头数据只在本机处理，用户可以随时关闭任意识别功能。

最终目标是形成莲心未来的本地视觉感知层：

```text
摄像头
  ↓
本地视觉处理
  ↓
统一状态与事件
  ↓
莲心 Agent / 对话系统
```

## 2. 当前开发进度

### 2.1 HandsDetector

HandsDetector 已完成独立实验室 MVP，当前链路为：

```text
CameraManager
  ↓
OpenCV 摄像头帧
  ↓
MediaPipe Hand Landmarker
  ↓
手部关键点
  ↓
GestureClassifier
  ↓
GestureState
  ↓
EventManager
  ↓
PyQt GUI / MockLianXin
```

已有能力：

- 摄像头读取、停止和资源释放
- 1280x720 优先、性能不足时降级到 640x480
- CPU + MediaPipe 手部识别
- 镜像视频显示
- OK 手势识别
- 大拇指手势识别
- 基于轨迹的挥手识别
- 连续帧确认、去抖和冷却机制
- 等待释放状态，避免持续保持手势时重复触发
- 独立识别线程，避免阻塞 PyQt 主线程
- 实时视频、识别状态和事件日志
- 参考项目 TFLite 分类器适配层

当前 TFLite 模型标签为：

```text
Open
Close
Pointer
OK
```

这不是完整的 0 到 9 数字模型。真正的数字识别需要后续采集数字手势数据并重新训练模型。

### 2.2 FaceDetector

FaceDetector 当前只有设计文档：

```text
Lab/FaceDetector/人脸识别与工位检测.md
```

目前尚未开始编写人脸识别代码、工位检测代码或独立 GUI。当前阶段属于需求和技术路线已确定、实现尚未开始。

规划中的能力：

- 本人识别
- 陌生人识别
- 无人状态识别
- 用户进入、离开和返回检测
- 工位驻留时间统计
- 长时间工作提醒
- SQLite 本地事件记录
- 后续向莲心发送视觉事件

## 3. 总体架构决策

不继续维护两个完全独立的视觉 GUI。新建统一的 `Lianxin Vision Lab`，由一个窗口承载人脸、手势和陪伴检测。

三个功能共享：

- 一个摄像头实例
- 一个视频帧分发链路
- 一个视觉 Worker
- 一个统一事件总线
- 一个统一日志系统
- 一个统一设置系统
- 一个本地数据库

这样可以避免多个程序分别占用摄像头，也避免重复读取和重复处理同一帧图像。

推荐总体链路：

```text
PyQt 主线程
  ├── 统一主窗口
  ├── 功能开关
  ├── 视频显示
  ├── 状态面板
  └── 事件日志

VisionWorker 线程
  ├── CameraManager
  ├── FrameDistributor
  ├── GestureFeature
  ├── FaceFeature
  └── CompanionFeature

事件层
  ├── VisionEvent
  ├── EventBus
  ├── SQLite Writer
  └── 后续莲心适配器
```

## 5. 统一界面设计

界面沿用 HandsDetector 当前的深色工程实验室风格，窗口默认约为 1200x720，允许缩放并保持视频比例。

```text
┌─────────────────────────────────────────────┐
│ 莲心视觉感知实验室                           │
├─────────────────────────┬───────────────────┤
│                         │ 功能开关          │
│                         │                   │
│     摄像头实时画面       │ ✓ 人脸识别        │
│                         │ ✓ 手势识别        │
│                         │ ✓ 陪伴检测        │
│                         │                   │
│                         │ 当前状态          │
│                         │ 用户：已识别       │
│                         │ 工位：工作中       │
│                         │ 手势：OK           │
├─────────────────────────┴───────────────────┤
│ 摄像头 | FPS | CPU | 人脸 | 双手 | 运行时间   │
├─────────────────────────────────────────────┤
│ 实时事件日志                                  │
├─────────────────────────────────────────────┤
│ [启动] [停止] [录入本人] [设置] [清空日志]     │
└─────────────────────────────────────────────┘
```

### 5.1 功能开关

每个功能必须是独立开关：

- 关闭人脸识别：不加载或不运行人脸识别模块
- 关闭手势识别：不运行手部推理和手势分类
- 关闭陪伴检测：不运行姿态和驻留分析
- 所有功能关闭时，仍允许仅打开摄像头作为预览

开关状态应在界面上清楚显示为：

```text
已启用 / 已关闭 / 加载中 / 初始化失败
```

### 5.2 状态面板

状态面板只展示用户真正关心的信息：

```text
摄像头       1280x720
FPS          29.8
人脸状态      用户已识别
手势状态      OK
陪伴状态      工作中
工作时长      01:20:32
运行时间      00:35:14
```

底层模型的详细调试信息进入日志，不直接堆积在主界面。

## 6. 分阶段实施计划

### 第一阶段：统一基础框架

目标是建立统一窗口、统一摄像头和统一 Worker，不实现完整人脸识别。

工作内容：

1. 新建 VisionLab 基础目录。
2. 建立统一 PyQt 主窗口。
3. 建立统一 CameraManager。
4. 建立 VisionWorker 线程。
5. 建立功能开关和模块生命周期管理。
6. 建立统一状态数据结构。
7. 建立统一事件总线和日志系统。
8. 实现摄像头画面单独运行。

验收标准：

- UI 不冻结。
- 摄像头只被打开一次。
- 摄像头异常时可以显示明确错误。
- 停止和退出时正确释放摄像头。
- 各功能开关可以独立切换。

### 第二阶段：迁移 HandsDetector

先接入已验证稳定的手势识别，保证现有功能不退化。

工作内容：

1. 将现有 HandDetector 接入 VisionWorker。
2. 将 GestureClassifier 适配为 GestureFeature。
3. 保留 GestureState 的连续确认、冷却和等待释放机制。
4. 保留 OK、大拇指和挥手识别。
5. 保留 TFLite 分类器作为独立旁路结果。
6. 关闭手势开关时停止相关推理。
7. 将原有手势事件转换为统一 VisionEvent。

验收标准：

- 现有 HandsDetector 测试结果基本一致。
- 关闭手势后不再产生手势事件。
- 摄像头和其他模块不受手势模块开关影响。
- 手势事件能进入统一日志。

### 第三阶段：人脸录入

人脸识别之前先完成本人录入，不直接硬编码用户特征。

流程：

```text
点击“录入本人”
  ↓
打开采集状态
  ↓
检测多帧人脸
  ↓
提取 ArcFace embedding
  ↓
计算稳定的平均特征向量
  ↓
保存本地用户记录
```

默认只保存：

- 用户称呼
- embedding 向量
- 创建时间
- 模型版本

默认不保存原始照片，除非用户明确选择保存。

### 第四阶段：人脸识别

基础链路：

```text
摄像头帧
  ↓
人脸检测
  ↓
人脸对齐
  ↓
ArcFace 特征提取
  ↓
Cosine Similarity 比对
  ↓
身份状态
```

统一输出：

```text
NO_PERSON
UNKNOWN_PERSON
USER_IDENTIFIED
STRANGER_IDENTIFIED
```

必须加入连续帧确认和状态保持，不能根据单帧结果直接触发进入、离开或陌生人事件。

### 第五阶段：陪伴与工位检测

第一版先使用人脸结果完成基础陪伴检测：

- 用户是否出现在画面中
- 用户是否持续出现
- 用户是否连续离开 30 秒
- 用户是否重新返回

后续再加入 MediaPipe Pose，判断用户是否位于工位区域以及姿态是否适合工作。

建议状态机：

```text
NO_PERSON
  ↓
PERSON_DETECTED
  ↓
USER_PRESENT
  ↓
WORKING
  ↓
AWAY
  ↓
RETURNED
```

输出事件：

```text
USER_ENTER
USER_LEAVE
USER_RETURN
STRANGER_DETECTED
LONG_WORK
```

### 第六阶段：SQLite 记录

仅在识别状态稳定后写入数据库，避免每帧写入。

建议表：

```text
user_presence
  id, date, enter_time, leave_time, duration

recognition_event
  id, timestamp, event_type, confidence

work_session
  id, date, start_time, end_time, duration
```

数据库写入应与视觉 Worker 解耦，避免磁盘 IO 阻塞识别线程。

### 第七阶段：莲心事件适配

视觉实验室稳定后，再提供统一事件接口给莲心：

```json
{
  "type": "user_return",
  "timestamp": "2026-08-18T18:30:20",
  "confidence": 0.96
}
```

视觉模块不直接调用 LLM、TTS 或对话逻辑，只负责输出结构化视觉事件。

## 7. 技术栈与依赖

基础阶段需要：

```cmd
python -m pip install PyQt5 opencv-python numpy mediapipe
```

人脸识别阶段再安装：

```cmd
python -m pip install insightface onnxruntime
```

第一版优先使用 CPU 推理，不立即引入 `onnxruntime-gpu`。原因：

- 当前目标是先验证功能链路和稳定性。
- GPU 版需要匹配 CUDA 和 cuDNN 版本。
- RTX 3060 可以作为后续优化方向，但不是第一阶段的必要条件。

InsightFace 模型首次运行可能自动下载。如自动下载失败，再单独处理模型缓存或手动下载问题。

## 8. 性能与线程要求

必须遵循以下原则：

- PyQt 主线程只负责界面。
- 摄像头读取和视觉推理运行在 Worker 线程。
- 数据库写入运行在独立写入队列或数据库线程。
- 功能开关改变的是模块执行状态，不直接销毁整个摄像头链路。
- 识别模块异常时只禁用对应功能，不导致整个实验室崩溃。
- 视频显示和识别频率可以分离。

目标设备：RTX 3060 Laptop 6GB、16GB RAM。

初始目标：

```text
摄像头显示：25~30 FPS
视觉识别：10~20 FPS
事件延迟：尽量低于 200ms
```

## 9. 隐私与安全边界

第一阶段及后续本地识别均遵循：

- 不上传摄像头画面。
- 不调用云端视觉 API。
- 不后台偷偷启动摄像头。
- 摄像头状态必须在界面中可见。
- 用户可以随时关闭任意功能。
- 默认不保存原始人脸照片。
- 只在状态变化或事件触发时记录数据库。
